# 阶段 3：账单更正实施与验收

基线：`4e0eff1`。范围来自已确认的分阶段 SOP；保持 SQLite、独立 Repayment、现有解析器和导入入口，不做历史批量修复、UI 美化或模型迁移。

## 实现决定

- 使用现有上传接口的两次请求：首次返回 HTTP 409 和差异；用户确认后重传文件及 `confirmation_token`。不保存原始附件、不增加待审表。无人值守导入只报告冲突，不替用户确认。
- 只在同一实体卡（或已支持的账户级账单）、同币种、同账单日的唯一对应关系中更新。同来源若卡片/账单日/币种结构变化，明确阻止自动覆盖；不同来源不能仅凭同银行同月份合并。
- 比较摘要金额、最低还款额、到期日和交易多重集合。交易身份包含日期、金额、币种、描述及实体卡归属；保留同日同额交易次数，不将集合去重用于交易。
- 确认指纹包含来源、解析结果和现有财务/人工状态。在 SQLite 写事务内重新比较，旧指纹失效时重新预览。
- 匹配交易保留原 ID 与人工字段。删除的旧交易有人工编辑、关联退款或被其他退款引用时，停止自动更正；同身份重复交易减少且含保护记录时也停止，不猜删除哪笔。
- 更新原 Statement，保留 Repayment。整个多账单更新、交易增删与来源记录在同一事务内提交，失败回滚。已被更正的旧来源重传仍需差异确认，不能悄悄回退。
- UI 只展示差异与确认/取消，复用现有提示方式。成功响应新增默认 `corrected=false` 标识，避免把更正成功显示为普通重复件。
