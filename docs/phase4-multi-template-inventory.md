# 阶段 4：多模板盘点与实现决策

基线：阶段 3 提交 cbe1879。本阶段仅做只读盘点与决策，不改动解析器、数据模型或导入行为。

## 方法

- 样本：私有 IMAP 样本目录（本地、未脱敏、不入库），9 家银行，1662 个文件（eml 826 / html 767 / pdf 68 / zip 1）。
- 盘点脚本 dev/phase4_inventory.py 为本地 dev 产物（不入库），仅提取结构指标：不回显账单内容、不联网、不渲染、不解压 zip。
- 模板签名：HTML 取"排序去重的标签词汇"，修正早期"按出现顺序"导致的签名裂变；PDF 取结构签名。
- 解析通过率分母：仅统计真正尝试解析的样本（全部 eml + 受支持银行的 pdf），排除 html/zip 的"仅格式存在"样本。
- 失败原因分桶：把解析器诊断消息映射到粗粒度桶，只输出桶名与计数，不回显原文。

注：原因桶仅覆盖解析器诊断（ParserError）；CCB 另有 1 例非解析器异常未入桶。

要点：
- 所有尝试样本都有 HTML 正文（NoHtmlBody=0），失败发生在银行解析器层，而非"无正文/纯文本通知"。
- 多数银行的主导失败是"字段提取缺口"（识别为账单但取不到必需字段），确有真实解析缺口，不能简单归因为"非账单邮件"。
- CGB/PAB 以"未识别/非账单"为主（66/64），需在识别层进一步区分"另一模板"与"非账单"。
- ICBC 有 42 例"多卡/歧义"安全拒绝（多还款汇总/多卡引用），属安全保护，不应通过放宽多卡安全来"修复"。

## 决策：本阶段不新增解析规则（暂缓实现）

依据 SOP"仅在有 2+ 真实模板的可靠证据时选银行实现；仅补当前样本证明需要的规则"：

1. 聚合计数不足以干净证明"2+ 真实账单模板 + 可安全修复的缺口"。签名长尾与字段缺口可能源于单模板内的可选字段/格式差异，需逐样本确认。
2. 设计新规则必须查看失败样本的真实 HTML 结构；私有样本未脱敏，按隐私边界不能在未脱敏/未授权下读取内容来设计规则。
3. ICBC 的主要失败是多卡安全拒绝，放宽它违背安全姿态，不属于"补模板"。
4. CGB/PAB 需先做识别层诊断，区分模板差异与非账单。

因此本阶段交付"盘点 + 原因诊断 + 暂缓决策"，不改动解析器、数据模型或导入行为。

## 推进所需证据

- 按银行提供脱敏后的失败样本（保留结构、去除个人信息），以确认是否为真实多模板及具体缺口。
- 对 CGB/PAB 做识别层诊断；对 ICBC 明确多卡/多汇总语义（与阶段 5 联动）。
- 获得读取/处理样本的明确授权后，再按"样本证明必要"的最小规则实现。

## 产物与边界

- 盘点脚本与完整报告为本地 dev 产物（dev/phase4_inventory.py、dev/phase4_inventory_report.json），不入库；本文档内嵌关键结果，自包含。
- 全程只读、不联网、不渲染、不回显账单内容；私有样本未脱敏，不用于测试。
